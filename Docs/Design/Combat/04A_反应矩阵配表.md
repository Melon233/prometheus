## 0. 配表规范

本案的表结构遵循项目的 Luban 配表管线，规范与目录职责见 [Docs/ConfigPipeline.md](../../Workflow/ConfigPipeline.md)。此处只摘录本案直接用到的约定：

## 1. 枚举定义（代码侧，不入表）

```csharp
// 八种元素身份；Anemo 与 Geo 只作为反应触发方，不在目标身上留存附着。
public enum ElementType { None = 0, Pyro, Hydro, Electro, Cryo, Dendro, Anemo, Geo, Physical }

// 附着强度档位，决定标称附着量与衰减时长。
public enum GaugeStrength { None = 0, Weak, Medium, Strong }

// 反应的结算方式，决定它进入伤害公式的哪个位置。
public enum ReactionCategory
{
    None = 0,
    Amplifying,      // 增幅：作为独立乘区放大本次伤害
    Transformative,  // 剧变：独立结算的第二笔伤害，不吃攻击面板
    Catalyze,        // 激化：以加算形式并入基础伤害
    Special          // 特殊：冻结、结晶、绽放、原激化，产物由 EffectDefinition 承载
}

// ICD 策略，见 04 第 4 节。
public enum IcdPolicy { Shared = 0, Independent, None }

// 附着判定键：八元素之外，再加三个以状态而非附着形式存在的伪元素，见 5 节。
public enum AuraKey
{
    None = 0, Pyro, Hydro, Electro, Cryo, Dendro, Anemo, Geo, Physical,
    Frozen = 20, DendroCore = 21, Quickened = 22
}
```

以上枚举已在 `Data/Excel/Defines/__enums__.xlsx` 中建好，由导表生成到 `Assets/Gen/Config/Prometheus/Config/`。**修改枚举请改表，不要改生成代码**——生成代码会在下次导表时被覆盖。

枚举是对应列的合法取值集合，导表遇到枚举外的字面量会直接失败并指出文件、Sheet、行列。

## 3. 配表：`ReactionMatrix`

**表名**：`ReactionMatrix`
**用途**：反应规则的唯一定义。新增或调整反应只应改这张表。

**行的语义**：`triggerElement` 命中带有 `auraElement` 附着的目标时发生什么。**顺序敏感**——火打水和水打火是两行。

| 列名 | 类型 | 描述 |
| --- | --- | --- |
| `reactionId` | string | 反应唯一标识，PascalCase |
| `triggerElement` | ElementType | 触发元素（本次攻击携带的元素） |
| `auraElement` | AuraKey | 目标身上已存在的附着，含三个伪元素状态，见 5 节 |
| `category` | ReactionCategory | 结算方式 |
| `priority` | int | 目标身上有多个附着时的判定优先级，数值大者先判 |
| `multiplier` | float | 增幅基础倍率 / 剧变反应倍率 / 激化倍率；`Special` 填 0 |
| `damageElement` | ElementType | 剧变伤害的元素；无独立伤害填 `None` |
| `auraConsumeRatio` | float | 消耗附着量 = 本次触发附着量 × 该值 |
| `triggerConsumed` | bool | 触发元素自身是否被完全消耗（不写入附着） |
| `emCoefficient` | float | 精通公式分子系数：增幅 2.78 / 剧变 16 / 激化 5 / 结晶 4.44 |
| `emDenominator` | float | 精通公式分母常数：增幅 1400 / 剧变 2000 / 激化 1200 / 结晶 1400 |
| `reactionBonusAttr` | string | 对应的反应加成属性位 ID，见 `05A` 第 3.5 节；`AttributeSlot` 建表后改为枚举 |
| `effectId` | string | 反应产物的 `EffectDefinition` ID；无产物留空 |
| `#confidence` | — | `Verified` / `NeedsReview` / `Custom`，见 README 数值置信度标记。`#` 前缀列不导出，仅供策划自查 |

该表 90 行，本案只给出锚点用于校验填表结果是否走在正确量级上：

| level | coefficient | confidence |
| --- | --- | --- |
| 1 | 17.17 | NeedsReview |

| 40 | 289.7 | NeedsReview |
| 60 | 590.2 | NeedsReview |

**填表方法**：在原神中用已知精通、已知等级的角色打固定抗性目标，读取剧变伤害数字反解等级系数。每 5 级取一个采样点，其余用采样点校验后的曲线拟合填充，并逐级复核与锚点的偏差。

**当前实现状态**：表已导出并被 `DamagePipeline` 按施加者等级读取（`TbReactionLevelCoefficient.Get(level).Coefficient`），因此代码链路已经打通，替换数据不需要改任何代码。

该表是全部剧变伤害的公共因子，填错会导致所有剧变数值系统性偏移，因此它是整个配表工作中优先级最高、也最不能凭经验估算的一张。

## 5. 伪元素与状态

三个 `auraElement` 取值不是真实附着，而是状态标记：

| 伪元素 | 含义 | 产生 | 消失 |
| --- | --- | --- | --- |
| `Frozen` | 冻结状态 | `FrozenHydro` / `FrozenCryo` | 时长耗尽或被碎冰 |
| `DendroCore` | 草原核实体 | `Bloom*` | 延时爆炸或被超绽放/烈绽放转化 |
| `Quickened` | 原激化状态 | `Quicken*` | 时长耗尽 |

它们与八元素共用 `AuraKey`，但取值段独立（20 起），因此判定只需一次区间比较。`ReactionResolver` 按 `priority` 降序取第一条命中行，伪元素行的优先级高于普通附着行。

**哪一行写入哪个状态**由 `producedAura` 列声明（`ElementType` 之外的 `AuraKey` 取值），**状态时长**由 `PseudoElementState` 表给出。两者都在配表里，代码不按 `reactionId` 前缀猜测。

### 已知的模型偏差：草原核

原神中草原核是**独立的世界实体**——它有自己的位置、上限五个、可以被生成它的敌人之外的目标引爆。本案把它建模为目标身上的一层状态，因此丢失了位置无关性与延时自爆。

这个偏差在一个场景下会显现：绽放保留双方附着，而火打水的蒸发（优先级 100）高于烈绽放（98），所以只要水附着还在，火伤永远打不出烈绽放。实体模型下这不成立，因为核与水附着不在同一个目标上。

草原核实体化与延时自爆属于 [90 差异台账](90_现有实现差异台账.md) 第 3 节 `EffectSystem` 扩展。

**冻结时长**不入 `ReactionMatrix`，由 `04` 第 5.6 节公式运行时计算：

```text
冻结时间(秒) = 2 × sqrt(5 × 冻结附着量 + 4) − 4
```

## 8. 反应判定流程

`ReactionResolver` 的查表顺序，这是把上述表转为运行时行为的唯一路径：

```text
Apply(trigger, strength, target)
 ①  ICD 门控：查 IcdGroup，本次是否允许附着
     └─ 不允许 → 返回 ReactionResult.None，不改变任何状态
 ②  收集目标身上全部候选附着（含伪元素状态）
 ③  在 ReactionMatrix 中筛选 triggerElement 匹配的行
 ④  与候选附着求交集，按 priority 降序取第一条
     └─ 无匹配 → 写入/刷新触发元素附着，返回 None
 ⑤  按该行结算：
     ├─ 消耗附着：auraGauge -= 本次附着量 × auraConsumeRatio
     ├─ triggerConsumed = false 时，触发元素也写入附着
     ├─ Amplifying → 填 ReactionResult.AmplifyMultiplier
     ├─ Catalyze   → 填 ReactionResult.CatalyzeAdd
     ├─ Transformative → 填 ReactionResult.TransformativeDamage（由管线独立结算）
     └─ effectId 非空 → 交由 EffectSystem 施加产物
 ⑥  附着量归零的元素从 AuraSet 移除
 ⑦  返回 ReactionResult
```

**步骤 ④ 只取一条反应**：单次攻击不会同时触发两种反应。目标身上同时有水与雷时，火命中优先触发哪个由 `priority` 决定（本表中蒸发 100 > 超载 90，因此火优先蒸发）。

## 9. 精通公式统一形式

三类反应的精通项共用同一形式，参数已在 `ReactionMatrix` 的 `emCoefficient` / `emDenominator` 两列中：

```text
精通项 = emCoefficient × EM / (EM + emDenominator)
```

| 反应类型 | emCoefficient | emDenominator | 最终形式 |
| --- | --- | --- | --- |
| 增幅 | 2.78 | 1400 | `基础倍率 × (1 + 精通项 + 反应加成)` |
| 剧变 | 16 | 2000 | `等级系数 × 反应倍率 × (1 + 精通项 + 反应加成) × 抗性区` |
| 激化 | 5 | 1200 | `等级系数 × 激化倍率 × (1 + 精通项 + 反应加成)` |
| 结晶 | 4.44 | 1400 | `等级系数 × 1.5 × (1 + 精通项)` |

把这四组参数放进表而非代码，使得后续调整精通曲线只需改表。

## 10. 填表与验收顺序

1. `GaugeStrength`（3 行，可直接实装）
2. `IcdGroup`（2 行，可直接实装）
3. `ReactionMatrix` 的 `Verified` 行（增幅 4 行 + 冻结 2 行 + 结晶 4 行 + 激化 2 行）
4. `ReactionLevelCoefficient`（90 行，实机反解，关键路径）—— **表已建立但数据是占位**：当前 90 行由本案 6 个锚点做单调三次（Fritsch-Carlson）插值填充，锚点行标 `NeedsReview`，其余标 `Placeholder`。插值保证过锚点且全程单调递增，但**不等于实机值**，仍需按下方填表方法逐级反解替换
5. `ReactionMatrix` 的 `NeedsReview` 行（剧变与草系，依赖第 4 步的系数才能校验）

第 4 步是整个配表工作的瓶颈：在它完成前，任何剧变反应的数值都无法验证。建议与第 1～3 步并行启动。

## 11. 验收用例
