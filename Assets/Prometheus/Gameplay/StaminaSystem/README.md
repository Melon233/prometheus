# StaminaSystem

体力池的唯一权威。按 [02 第 5 节](../../../../Docs/Design/Combat/02_攻击与连段.md)：上限 240、停止消耗约 1 秒后开始恢复、恢复约 25/秒。

## 为什么是 System 而不是属性

体力**全队共享、不随切人重置**。做成 `PropertyComponent` 上的逐角色资源就会在切人时换掉池子——而原神里换人不回体力，这是冲刺与滑翔续航的核心约束。

因此池子由系统持有，角色只贡献**消耗侧**的修正：`PropertyType.StaminaConsumptionReduction` 读的是**发起这次消耗的那个角色**的面板。同一次冲刺由谁发起，就按谁的减免算。

## 两种消耗语义

| 入口 | 语义 | 用于 |
| --- | --- | --- |
| `TryConsume` | **全有全无**，不足时一点不扣 | 重击、冲刺起步、攀爬蹬跳 |
| `ConsumeContinuous` | 扣多少算多少，允许扣空 | 冲刺持续、攀爬、游泳、滑翔 |

分成两个不是为了方便：原神里体力不够就放不出重击，而不是放出一个削弱版本，所以一次性消耗必须全有全无；而冲刺该在体力见底的那一刻停下，所以持续消耗必须允许扣空并如实返回实际扣除量。合成一个会让调用方处理一个不存在的中间态。

## 恢复的帧边界

跨越恢复延迟阈值的那一帧**只按阈值之后的那一段**恢复。直接用整个 `dt` 会把仍处于延迟窗口内的时间也算成恢复时间，结果是**帧率越低恢复越快**——这类偏差只在低帧率设备上显形，极难复现。有用例锁住这条。

## 消耗量在哪配

一次性消耗的量随**攻击段落**走：`TbAttackSegment.staminaCost`。它与倍率、附着档位同源，因为「这一段消耗多少体力」和「这一段打多少伤害」是同一个策划在同一行里决定的。

持续消耗（冲刺、攀爬、游泳、滑翔）的速率尚未配表，属排期第 8 步。

## 上限全局唯一

体力上限 = 基础 240 + **七天神像**累计加成。它不随角色变化：池子全队共享，能提升它的只有世界进度。

因此 05A 里那个逐角色的 `PropertyType.Stamina` 属性位**已作废**（枚举值保留占位，见 `ARCH-META-002`）。角色能影响的只有消耗侧的 `StaminaConsumptionReduction`。

提升上限时当前体力同额增加——解锁神像立刻就能多冲刺一段，而不是要等恢复把新容量填满。

`SetStatueBonus` 接受的是**累计总量**而不是增量，重复传入同一个值不会重复生效：神像解锁状态会随存档重放，增量语义在重放时会翻倍。
