# 游戏客户端 AI 工作流设计方案

> 目标：用「策划组 / 开发组 / 美术组 / TA组 / 测试组 / PM」六个顶层节点，搭建一套高度规范化的 AI 工作流；每个流程都能轻松地人工审查并介入干涉。

---

## 一、底层原则

1. **单一事实源（Single Source of Truth）**：策划案是唯一契约，下游所有节点只引用它，不做二次转述。谁发现歧义，改的是案子本身，不是各自脑补。
2. **门禁制（Gate）**：每个节点的产出必须过一道「评审门」才能流入下游；每道门都有明确的人工「批准 / 驳回 / 修改」动作，AI 只负责提案和预审。

---

## 二、阶段总览

### 阶段 0 · 立项（主策划 + PM）
- 主策划输出《立项策划案》。
- PM 定义版本范围与里程碑（v0.1 = 战斗关卡 MVP）。

### 阶段 1 · 策划细化（策划组）
- 主策划输出《战斗系统策划案》初稿。
- 策划组 AI 三件事：
  - **Web 检索**：竞品机制、同类玩法、行业标准。
  - **自主评审**：产出《评审报告》——一致性 / 完整性 / 歧义 / 依赖闭环。
  - **人工润色**：人结合评审报告裁决，AI 落回文档。
- 关键产出：**跨角色可读的 Feature Spec**（非散文），字段见第四节。

### 阶段 2 · 需求拆解与任务编排（PM + AI）
- 每个 feature 拆成可执行 ticket，标注：依赖、负责组、验收标准、估算。
- 产出：Backlog + 依赖图。
- 人工介入点：审依赖顺序、砍范围、调优先级。

### 阶段 3 · 并行生产（开发组 / 美术组 / TA组 三线并行）
- 见第五节「三线并行解耦」。

### 阶段 4 · 集成（TA + 开发）
- 资源接入、性能检查、规范校验。
- **集成门**：TA 审资源规范、开发确认功能可运行。

### 阶段 5 · 测试（测试组）
- 消费 Feature Spec 的「验收标准 (AC)」生成测试用例。
- 三层：自动化 + AI 探索性测试（边界/异常）+ 人工手测。
- 缺陷回环：bug → 修复 → 复测，每个 bug 反向挂到 feature。

### 阶段 6 · 验收与复盘（PM + 全员）
- 对照里程碑验收。
- 复盘回流：评审意见、常见歧义、高频 bug 沉淀回规则库 / prompt 模板。

---

## 三、贯穿全程的三条介入机制

| 机制 | 作用 |
|---|---|
| 唯一 ID 全链路追踪 | feature → ticket → code → asset → 测试用例 → bug 全挂同一 ID |
| 每道门的人工裁决权 | AI 永远只出「提案 + 预审报告」，通过/驳回/修改在人手里 |
| 规则库沉淀 | 每次人工驳回理由回填成下游 AI 约束，越用越准 |

## 四、节点一：Feature Spec 模板字段细则

这是全流程契约，必须钉死。每个 feature 一个条目，字段如下：

### 核心字段（必填）

| 字段 | 说明 | 消费方 |
|---|---|---|
| `Feature ID / 名称` | 唯一标识，如 `CMB-001 三段连击` | 全员 |
| `一句话目标` | 解决什么问题（一句话） | 全员 |
| `触发条件` | 何时 / 何条件下生效 | 开发 / 测试 |
| `详细规则` | 分步骤、无歧义描述 | 开发 |
| `数值表` | 初始值 + 可调范围 | 数值策划 / 开发 |
| `状态与边界` | 异常、冲突优先级、空输入 | 开发 / 测试 |
| `验收标准 (AC)` | Given/When/Then 可测试写法 | 测试 |
| `依赖与影响` | 依赖哪些系统、影响哪些系统 | PM / 开发 |
| `美术需求` | 模型/动画/特效/UI/音效 + 规格 | 美术 / TA |
| `风险与待定项` | 未决问题清单 | PM |

### 字段写作规范（让 AI 可消费的关键）

1. **禁止模糊词**：`大概`、`适当`、`流畅`、`感觉不错` → 必须量化（`0.15s 内`、`≤2% 偏差`）。
2. **AC 一律 GWT 写法**：
   - `Given`（前置状态）/ `When`（触发动作）/ `Then`（可观测结果）。
   - 例：`Given 玩家血量 100，When 受到 30 点伤害，Then 血量变为 70 且播放受击动画`。
3. **数值表带区间**：`伤害 = 10（可调范围 5–20）`，区分「设计值」与「可接受范围」，避免数值策划与程序各执一词。
4. **美术需求带规格**：不写「一个炫酷的爆炸特效」，而写 `爆炸特效：循环时长 ≤1s、最大粒子数 ≤200、颜色遵循战圈色板、透明通道 PNG`——TA 能据此做性能预算。
5. **依赖显式声明**：写清「本 feature 依赖 CMB-002 的倒地状态」，让 PM 能自动生成依赖图。

## 五、节点二：阶段 3 三线并行解耦

三线并行最大的问题是：**开发等美术资源、美术受 TA 规范约束、TA 规范又依赖策划定稿**。解耦的核心是把「依赖」变成「契约先行、实现并行」。

### 解耦策略

1. **契约先行（Contract-first）**：
   - 策划案一旦过门，先由 TA 从「美术需求」字段提取出**资源规格契约**（命名、目录、格式、性能预算、尺寸/面数上限）。
   - 开发组拿到的是**接口契约**（数据结构、函数签名、占位资源路径），不拿最终美术成品。
   - 于是三线拿到的是「契约」，不是「彼此的成品」，互不阻塞。

2. **占位资源（Placeholder / Proxy）**：
   - 开发组用灰盒 / 占位资源（白模、占位音效、占位贴图）先行开发。
   - 美术组按规格产出正式资源，命名与路径必须与契约一致。
   - 集成阶段「换资源」只是路径替换，不涉及逻辑改动。

3. **TA 居中仲裁**：
   - TA 是开发与美术之间的「编译期接口」。
   - 美术产出先过 TA 的**规范校验门**（尺寸、面数、格式、命名自动化校验），再进开发。
   - 冲突时 TA 仲裁：要么改资源，要么改契约（改契约必须回写 Feature Spec）。

4. **依赖隔离（接口抽象）**：
   - 开发组针对「数据 / 表现」解耦：逻辑层只依赖数据接口，表现层（动画、特效）通过事件 / 资源 ID 触发。
   - 美术换版本不影响逻辑，逻辑改触发不影响美术。

### 并行编排示意

```
策划案定稿（契约源）
        │
        ├──► TA：提取资源规格契约 ──► 下发美术组（硬约束）
        │         │
        │         └──► 定义接口契约 ──► 下发开发组
        │
        ├──► 开发：用占位资源 + 接口契约 开发逻辑
        │
        └──► 美术：按规格契约 产出正式资源
                     │
                     ▼
                TA 规范校验门
                     │
                     ▼
                集成（换资源）
```

### 关键人工介入点

- **契约确认门**：TA 产出的规格契约 + 接口契约，需 PM / 策划确认一次，之后三线才可并行（防止契约本身有歧义导致全盘返工）。
- **规范校验门**：美术资源不合规时，TA 驳回并给出具体清单，美术按清单改。
- **变更控制**：集成阶段若发现契约要改，必须走「变更评审」，回写 Feature Spec，而不是私下改。

## 六、下一步建议

1. 钉死 Feature Spec 字段模板（做成一页可填写的表单 / 模板文件）。
2. 定 TA 的「资源规格契约」字段（命名规则、目录、性能预算表）。
3. 定每道「评审门」的通过标准与人工操作界面。
